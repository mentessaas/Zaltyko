01

Resumen ejecutivo

Zaltyko es un SaaS multi-tenant para academias de gimnasia con una base técnica notablemente madura: ~189 tablas Drizzle, 306 rutas API todas bajo wrappers de autorización, RLS validada automáticamente en CI (~330 políticas), ledger de migraciones con SHA-256, 132 suites de tests unitarios, 17 specs E2E Playwright, auditoría WCAG 2.2 AA y gates estáticos propios (gate:all, verify:production).

Sin embargo, hay una tensión clara entre la inversión técnica y el resultado comercial: el funnel real es 2 academias Free, 0 leads, 0 suscripciones, 0 entrevistas de pricing. Y antes de crecer, hay dos problemas de seguridad que deben resolverse esta misma semana.

Hallazgo más grave: existe una clave service_role de Supabase hardcodeada en scripts/test-dashboard-flows.ts y ya presente en el historial de git. Borrar el archivo no basta: hay que rotar la credencial inmediatamente.
Segundo hallazgo: los security headers prometidos (CSP, HSTS, X-Frame-Options…) figuran en comentarios de next.config.mjs como si se aplicaran desde middleware, pero el middleware no los implementa y no están en vercel.json. La app de producción va sin ninguna de estas protecciones.
Tesis general: el proyecto no necesita más infraestructura ni más módulos. Necesita cerrar las dos brechas de seguridad, decidir la duplicación legacy /dashboard/* vs /app/[academyId]/*, reducir el burn de meta-trabajo de agentes (118,7% del presupuesto mensual) y pasar a validar comercialmente con clientes reales.

Arquitectura

Puntos fuertes

  • Aislamiento multi-tenant serio: wrappers withTenant / withSuperAdmin / withBearerTenant, auditoría clasificó 272/272 rutas con 0 mutaciones sin auth conocida, escalada cross-tenant cerrada y documentada.
  • Disciplina de datos: ledger SHA-256 con advisory lock para migraciones Supabase, prohibido drizzle-kit push remoto, verificación RLS automatizada en CI.
  • Middleware sólido: i18n → rate-limit mutantes (sliding window sobre Vercel KV) → gate super-admin con verificación HS256 real (timingSafeEqual) fail-closed.
  • Vault operativa excepcional: decisiones, changelog, riesgos y backlog con evidencia y fechas — trazabilidad poco común en proyectos de este tamaño.
  • Código limpio: solo 14 TODO/FIXME/HACK en ~200k líneas y 0 console.log.

Calidad y testing

La infraestructura de calidad es muy superior a lo habitual en un proyecto pre-revenue: gates estáticos con self-tests (unbounded-reads, auth-before-validate, orphan-app-route), auditoría de env contract, verificación semántica de RLS, detección de políticas permisivas con allowlist aprobada, SBOM CycloneDX, y CI en GitHub Actions con jobs de dependencias, lint/typecheck, vitest coverage, build, smoke Chromium y validate-rls.

  • Release gate: pnpm verify:production orquesta 9 comprobaciones (279 APIs, RLS, lint, typecheck, 435 pruebas, build de 216 páginas).
  • E2E: flujos críticos autenticados sin aprovisionar usuarios fabricados; SCA/3DS, Stripe Connect, role smoke, coach workspace.
  • a11y: axe WCAG 2.2 AA + specs dedicadas (toast live-region, focal points, journeys).
  • Seguridad: config dedicada vitest.security.config.ts y test de contrato PWA.
  • Gaps: mobile/ con 1 test; falta spec E2E que falle si desaparecen CSP/HSTS (evitaría regresiones de headers).
04

Seguridad

✓ Fortalezas reales

  • Stripe webhooks: firma constructEvent + tolerancia 300s, idempotencia, también en Connect. Mailgun con comparación timing-safe.
  • Rate limiting sliding window en middleware para toda mutación API, con exclusión justificada de webhooks/crons.
  • Super-admin: HS256 con timingSafeEqual, validación exp/iat con skew, fallback remoto a Supabase.
  • Cron auth: CRON_SECRET timing-safe, falla cerrada (503).
  • Zod en 182+ route files; gate vigila orden auth→validación.
  • ~330 políticas RLS con endurecimiento iterativo documentado.

✕ Huecos encontrados

  • CRÍTICO: service_role key de Supabase hardcodeada en scripts/test-dashboard-flows.ts; anon keys en auto-configure-db.ts y setup-db-connection.ts. La service_role vive en el historial git → rotar ya.
  • ALTO: cero security headers en producción (sin CSP, HSTS, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy).
  • MEDIO: build silencia errores de tipos/lint fuera de CI.
  • MEDIO: Docker prod descuidado (Node desalineado, npm install sin lockfile, root).
  • BAJO: /api/dev/session excluido del rate limit por prefijo (hoy seguro por doble gate NODE_ENV, pero superficie evitable).
  • BAJO: tokens de invitación en claro (único item P0-Día-4 abierto con alcance real).
