## Design specificity verdict

The strongest vertical-specificity moment is **`MyDashboardPage.tsx:322-352`**
— first-person Spanish copy that adapts per persona and per
`specialization.labels.athletesPlural` ("Tus deportistas" / "Tus gimnastas"
depending on the academy's sport config). This is real vertical specificity,
not just translation: the same code reads differently for an artística vs
rítmica vs masculina academy.

The weakest vertical-specificity moment is the **5 stat cards at
`MyDashboardPage.tsx:244-336`** — pastel `bg-{purple,emerald,blue,amber}-100`
+ raw `shadow-[...rgba...]` strings, the canonical Vercel/AI template
"stat with rounded icon background". This file ships the first impression
for parent/athlete personas, and it diverges from every other dashboard
page visually.

## What's working

- **Persona routing is explicit and intentional.** `app/page.tsx:26` resolves
  coach→`/coach`, parent/athlete→`/my-dashboard`, owner/admin/super_admin→
  `/dashboard`. No one lands on the wrong surface by default.
- **Auth gates are layered.** Layout (`layout.tsx:182`) catches "no access
  at all", individual pages (`dashboard/page.tsx:89`, `billing/page.tsx:63`,
  `coach/page.tsx:143`, `my-dashboard/page.tsx:147`) re-check after the
  layout lets them through. Defence-in-depth is real (B).
- **Zero orphan files** (B). All 4 extracted page-level components
  (`NewAthletePageClient`, `DiscountsPage`, `MyDashboardPage`, `WhatsAppPage`)
  are wired. The `(site)/` orphan problem does NOT replicate here because
  pages delegate to `src/components/<module>/`, not to sibling files.
- **Zero hardcoded hex colors** in `src/app/app/` (B) — brand token
  enforcement is intact in the dashboard. The only raw palette escape is
  pastel `bg-*-100` in `MyDashboardPage.tsx`.
- **87+ API routes** correctly use the `.nullable().optional()` Zod pattern
  (B). No live silent-400 trap found in scope.
- **Loading.tsx coverage** is 63/66 (B) — better than the `(site)/` tree.
- **Spanish-first throughout** (A) — no English drift found in any UI
  string in scope. `MyDashboardPage.tsx:127-135` localises
  `DAYS_OF_WEEK`. Specialization-aware vocabulary via
  `specialization.labels.athletesPlural` is genuine vertical fit.
- **Mobile nav respects iOS notch** (`MobileAcademyNav.tsx:70` safe-area).
- **`AcademySidebar.tsx:126`** has `aria-current="page"`. Navigation
  registry's `isAcademyNavigationActive` correctly uses exact-match for
  dashboard to avoid the dashboard-ancestor problem.

## Priority issues (synthesis from A + B)

### [P0] `/app/admin/dashboard` has NO auth gate — anyone can read MRR/global metrics

- (B) `src/app/app/admin/dashboard/page.tsx:1-155` is a server component
  importing `db` directly (lines 4-10). Queries: `getAcademiesByPlan()`
  (line 21), `getEstimatedMRR()` (line 30), `getGrowthMetrics()` (line 40),
  `getTopAcademies()` (line 85). No `withSuperAdmin`, no
  `verifyAcademyAccessForProfile`, no `supabase.auth.getUser()`. Any
  visitor to `/app/admin/dashboard` reads aggregate commerce data.
- (A) Confirms the same file is structurally an orphan — it's under
  `/app/...` (the academy-prefixed tree) but doesn't follow the same
  auth/role chain, isn't in the nav registry, and isn't discoverable from
  the academy sidebar. Same finding, different angle: B sees the security
  hole, A sees the structural orphan. Both P0.
- Impact: data leak of platform-level metrics + the classic "two surfaces,
  only one gated" trap. Mitigated only by obscurity (no nav link).
- Suggested command: `/impeccable refine` — relocate to
  `src/app/(super-admin)/super-admin/dashboard/` (inherit
  `withSuperAdmin`), or wrap the page in `withSuperAdmin(async () => { ... })`.

### [P0] 61 of 63 route segments have no `error.tsx` boundary

- (A) Only `coach/today-simple/error.tsx` and `dashboard/at-a-glance/error.tsx`
  exist. `find src/app/app -name "error.tsx"` → 2 hits.
- (B) Confirms 2/66 (3%). 64 pages inherit no contextual recovery. Any 500
  on athletes, billing, settings, attendance, classes, groups, coaches,
  evaluations, events, notifications, announcements, all 7 reports
  sub-routes, support, etc. surfaces the framework default.
- (B) Additionally: `0/66` `not-found.tsx` files. `notFound()` is called
  from at least 5 pages (athletes, coaches, settings, billing, my-dashboard)
  but a 404 hits the framework default.
- Impact: operator risk for a product with 2 real customers on a daily-use
  surface. The two existing `error.tsx` files already have the right
  pattern (`role="alert"`, digest-logged, `Reintentar` + `Volver` escape);
  the fix is to lift the pattern, not invent it.
- Suggested command: `/impeccable scaffold` — single shared
  `src/app/app/[academyId]/error.tsx` + `not-found.tsx` covers 97% of
  routes. ~50 lines.

### [P0] Mobile nav auto-hides on scroll-down with no return affordance

- (A) `MobileAcademyNav.tsx:30-37` hides on scroll-down, only re-shows on
  scroll-up. No tap-to-show, no FAB, no persistent bottom-edge swipe. On
  long lists (athletes, attendance, classes), the user scrolls, realizes
  they need the nav, has to scroll up first. Coach on gym floor with one
  hand: "where did the bottom nav go".
- Impact: coach persona pain (most mobile-heavy), no escape hatch.
- Suggested command: `/impeccable refine` — keep auto-hide, but add
  edge-tap affordance or persistent thin grip indicator. Or accept a 56px
  persistent bar for this user base (A's provocative Q4).

### [P1] Settings page `loadSettings()` swallows non-ok responses silently

  branch mirroring the `error.tsx` pattern.

## Provocative questions

1. **What if `OwnerAttentionPanel` should BE the default `/dashboard`?**
   Current `/dashboard` is a vanity board with 30 widgets; the actual
   "what do I do today" brief lives at `/dashboard/at-a-glance` — one
   extra click away and not in the sidebar. Owner at 8am asking "what's
   on fire" deserves that to be the landing.
2. **What if `/app/admin/dashboard` is the vestigial start of a "platform
   view" that was abandoned?** (B) Route exists, renders coherent data,
   has no auth gate (P0), no nav link (orphan). Either commit (move
   under `(super-admin)/` + link it) or delete it.
3. **What if `AthletesTableView` import-CSV button is the right primary
   CTA for 2-academy scale?** Empty state has it; no onboarding tour
   points new owners at it on day 1.
4. **What if mobile nav auto-hide is hurting more than helping for this
   user base?** Coaches on the gym floor with one hand. Auto-hide is
   great for reading news; here it forces a "where did the nav go"
   moment. Persistent 56px bar might cost less screen real estate than
   the lost nav.
5. **What if the `error.tsx` rollout is the highest-leverage polish for
   this surface?** Two boundaries in 138 files is real risk; pattern
   already exists in two files and could be lifted to the parent
   `[academyId]` route in one commit. Covers 97% of failures with one
   file change.
6. **What if `redirect()` chains are a hidden UX tax for coach and
   super-admin personas?** Every role has at least one silent redirect.
   If we counted "redirects encountered per typical session", coach +
   super_admin would feel it more than owner. Pattern is correct
   security-wise; experience is "where did I just land".
7. **What if the entire `/app/[academyId]` tree is over-built for 2
   academies?** 138 files, ~63 route segments, ~30 dashboard widgets, 7
   report sub-routes, 6 billing sub-routes. The "honest scale" principle
   from PRODUCT.md says most of this is future-feature debt. But the UX
   itself, once you find yourself in it, works.
8. **What if the auth gate on `/app/admin/dashboard` is the most
   important security finding of the year so far?** (B) No
   `withSuperAdmin`, no `verifyAcademyAccessForProfile`, no
   `supabase.auth.getUser()`. Any visitor reads MRR / plan-breakdown /
   top-academy aggregate data. Same data the `(super-admin)` surface
   protects. Easy to ship a fix (move file + inherit layout), high
   impact.
