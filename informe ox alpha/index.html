Un SaaS multi-tenant para academias deportivas con ingeniería defensiva poco común: resolución de tenant desde base de datos, rate limiting que falla cerrado y gates estáticos propios. Los riesgos reales viven en los bordes, no en el núcleo.

Informe técnico generado por Ox Alpha · Next.js 15.5 · Supabase · Drizzle · Stripe

Veredicto

El proyecto está listo para crecer sobre bases sólidas, pero hay cuatro cosas que arreglaría esta semana: las cabeceras de seguridad que se creen aplicadas y no lo están, el typecheck roto que el build silencia, la dependencia xlsx instalada fuera del registro oficial y las 35 rutas API fuera de convención.

Lo que está muy bien

  • El tenant se resuelve siempre desde membresía en BD; jamás del input del cliente.
  • Rate limiting fail-closed en producción: si Redis falla, responde 429.
  • Gates estáticos caseros: reads acotados, auth-before-validate, rutas huérfanas.
  • Tres webhooks (Stripe, Lemon Squeezy, Mailgun) con verificación criptográfica real.
  • Migraciones SQL versionadas con ledger SHA-256 y pasadas de hardening RLS.

Lo urgente

  • Sin CSP, HSTS ni X-Frame-Options, aunque next.config.mjs:7 afirma lo contrario.
  • pnpm typecheck falla hoy y el build tiene ignoreBuildErrors.
  • xlsx llega de un tarball CDN, fuera de npm.
  • 35 de 306 rutas API fuera de convención; 3 aún devuelven { ok: true }.

Base de datos

83 archivos de esquema (~4.380 líneas) más plantillas por deporte. Diseño disciplinado, con una excepción que exige disciplina extra.

  • Multi-tenancy consistente: casi toda tabla lleva tenantId NOT NULL + academyId FK ON DELETE CASCADE. 332 índices, 76 únicos, compuestos tenant-first sistemáticos.
  • 200 foreign keys, todas con onDelete explícito: cero comportamiento implícito.
  • Soft deletes con deletedAt indexado donde corresponde; CHECK constraints declarados en Drizzle.
  • Sport-config: tablas template por disciplina que impulsan etiquetas como «Gimnastas». Decisión de producto bien modelada.
  • RLS robusto: 48 migraciones versionadas, 411 políticas, scripts de auditoría semántica dedicados.

Dualismo de migraciones

Conviven Drizzle generado (drizzle/) y SQL manual (supabase/migrations/). El ledger SHA-256 los reconcilia, pero un agente despistado puede aplicar por el camino equivocado. Es deuda de proceso, no de código: documentar el camino único y gatearlo.

Rendimiento

Buenas prácticas aplicadas donde importa; margen claro en caché y peso del cliente.

  • 37 dynamic imports estratégicos (charts, hubs, swagger) y 27 componentes memoizados.
  • 18 usos de next/image, cero tags <img> raw; AVIF/WebP con escalera completa de device sizes.
  • geo-loader con lazy import de datasets de 1.654 líneas; optimizePackageImports configurado.
  • 209 declaraciones force-dynamic: prácticamente todo sin caché. Correcto funcionalmente, headroom desperdiciado.
  • 422 componentes «use client» vs 264 server: el bundle cliente carga la mayor parte de la app.
  • Triple observabilidad en cliente (Sentry + PostHog + Vercel Analytics): coste de arranque acumulado.
  • Build sin typecheck ni lint: errores pueden llegar a previews de Vercel.

Plan de mejoras priorizado

Ordenado por impacto sobre riesgo. Nada de esto fue aplicado: es propuesta. Cada cambio debería registrarse en vault/06-Roadmap-y-Tareas/Backlog priorizado.md según la guía del vault.

  1. P0

    Añadir cabeceras de seguridad reales

    CSP con nonce, HSTS, X-Frame-Options, X-Content-Type-Options y Referrer-Policy en middleware o next.config; corregir el comentario falso de next.config.mjs:7-9. Esfuerzo bajo · impacto muy alto.

  2. P0

    Arreglar typecheck y devolverlo al build

    Corregir scripts/test-dashboard-flows.ts:30 y quitar ignoreBuildErrors gradualmente para que nada roto llegue a Vercel. Esfuerzo bajo · impacto alto.

  3. P0

    Sacar xlsx del CDN

    Sustituirlo por un paquete del registro (exceljs o SheetJS publicado). Esfuerzo bajo-medio · impacto alto.

  4. P1

    Unificar authz y eliminar el caso especial events

    Extraer la lógica compartida entre withTenant y withBearerTenant a un módulo común; documentar o eliminar el bypass de events. Esfuerzo medio · impacto alto.

  5. P1

    Rate limiting atómico y sin doble conteo

    Pipeline o script Lua en Redis para la ventana deslizante; decidir una sola capa de limitación. Esfuerzo medio · impacto medio-alto.

  6. P1

    Cerrar la brecha de convenciones API

    Migrar las 3 rutas restantes a apiSuccess/apiError y evaluar integrar family/me dentro del estándar authz. Esfuerzo bajo · impacto medio.

  7. P2

    Consolidar rutas duplicadas

    Redirects 301 de las ~66 páginas sueltas hacia (site)/(public); gatear la ruta dev. Esfuerzo medio · impacto medio.

  8. P2

    Gatear cobertura y llevar RLS a CI

    Thresholds mínimos en Vitest y tests de semántica RLS contra Postgres efímero en CI. Esfuerzo medio · impacto medio.

  9. P2

    Adelgazar dependencias de producción

    swagger-ui-react como dynamic import dev-only; consolidar icon libraries y parsers CSV; evaluar axios→fetch. Esfuerzo bajo · impacto medio.

  10. P2

    Caché selectiva

    Auditar los 209 force-dynamic caso por caso e introducir ISR/revalidate en lecturas públicas y directorio. Esfuerzo medio-alto · impacto medio.

  11. P3

    Higiene de repo

    Mover MDs de análisis a docs/, quitar .bak y tsbuildinfo del tracking, arreglar campo «main». Esfuerzo mínimo · impacto bajo.

  12. P3

    Cerrar TODOs funcionales

    Emails a padres y payment method de Stripe, o moverlos formalmente al backlog de producto. Esfuerzo medio · impacto producto.

  13. P3

    Modernizar tooling de largo plazo

    ESLint 8→9 y plan de salida de @vercel/kv antes de cualquier anuncio de deprecación. Esfuerzo medio · impacto a futuro.
