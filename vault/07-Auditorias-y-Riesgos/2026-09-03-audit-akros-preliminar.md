## EXECUTIVE VERDICT (preliminar)

**YES WITH LIMITATIONS** — El data model soporta el dominio de Akros mejor de lo esperado.
Las limitaciones son UX/workflow, no arquitectura.

## A. WHAT ALREADY WORKS — Evidencia del schema

### Academia
✅ `academies` + `academySportConfigs` (multi-tenant via withTenant)
✅ Multi-sede posible via `academies.id` único + `tenantId`

### Horarios y sesiones (LO QUE AKROS NECESITA)
✅ `classes` con: weekday, startTime, endTime, capacity, apparatus[]
✅ `autoGenerateSessions` + `autoGenerateDaysAhead` — el sistema AUTO-GENERA sesiones
✅ `class-sessions` con sessionDate, status (scheduled/completed/cancelled)
✅ Sport config separado: sportConfigId permite configurar programa por academia
✅ `class-exceptions` para excepciones de horario
✅ `class-coach-assignments` (M:N) — múltiples coaches por clase

### Atletas
✅ `athletes` con: dob, level, **levelCode + categoryCode + ageCategory + competitiveLevel + primaryApparatus**
✅ `athlete-sport-configs` (tabla de unión) — permite UN atleta con MÚLTIPLES programas/disciplinas
✅ `athlete-assessments` + `assessment-scores` — evaluaciones
✅ `athlete-invitations` — invitaciones formales

### Entrenadores
✅ `coaches` con bio, specialties[], certifications (jsonb), socialLinks
✅ `class-coach-assignments` — asignación flexible
⚠️ **No hay modelo explícito de "substituciones temporales"** — un coach assignment es permanente. ¿Workaround? Reasignar al substituto; pero requiere revertir manualmente.

### Eventos / Camps / Competiciones
✅ `events` con: category[], level (enum), discipline (enum), eventType (enum), competitionTypeCode, registrationStartDate/EndDate
✅ `event-registration` (inscripción a evento)
✅ `event-invitations` (invitar atletas a evento)
✅ country/province/cityName — ubicación del evento
✅ `isPublic` para eventos visibles al público

### Federaciones (preparado pero no completo)
✅ `federative-licenses` — existe la tabla
✅ `categoryCode` + `competitiveLevel` en atletas
⚠️ No hay modelo de "Season" (temporada federativa), no hay "Competition" separado de "Event" (eventos genéricos)
⚠️ Para Akros con gimnastas en competición oficial, esto requiere ABSTRACCIÓN (no hardcoded)

### Billing / Cuotas
✅ `subscriptions`, `charges`, `billing-invoices`, `billing-items`, `payment-attempts`, `refunds`
✅ Stripe como PSP
✅ `discounts` + `discount-campaigns` + `discount-usage-history`
⚠️ **Cuotas recurrentes de Akros:** el modelo soporta suscripciones pero NO hay evidencia de tarifas recurrentes específicas de academias de gimnasia (mensualidades, packs de horas, multi-descuento por hermanos, etc.) — probablemente requiere configuración.

### Asistencias
✅ `attendance-records` por sesión/atleta con status (present/absent)
✅ `athlete-documents` para documentación deportiva

### Multi-tenant + RLS
✅ `withTenant` wrapper en TODAS las APIs (pattern enforced)
✅ `tenantId` propagado a todas las tablas
✅ RLS policies (mencionado en AGENTS.md)

## B. WORKS WITH FRICTION — Lo que existe pero tiene UX floja

- Auto-generación de sesiones: existe el flag, no sé si UI lo expone bien
- `allowsFreeTrial`, `waitingListEnabled` — flags existen pero UX no probada
- `cancellationPolicy` (standard/flexible/strict) — definido, sin UI clara
- Sport config jerárquico (País→Disciplina→Rama) — modelo rico, UI probablemente requiere configuración cuidadosa
- 83 tablas — onboarding probablemente complejo

## C. CRITICAL BLOCKERS (hipótesis — no probadas)

1. **UX de "niveles internos + categorías externas" del atleta**: el schema lo soporta pero la UI probablemente NO muestra `levelCode` + `categoryCode` + `ageCategory` + `competitiveLevel` como campos editables en el perfil del atleta con sus relaciones claras.

2. **Substituciones temporales de coaches**: NO hay modelo. Workaround: cambiar el assignment (problemático para historial).

3. **Onboarding de academia nueva**: 83 tablas + authz con `withTenant` estricto. Setup inicial probablemente requiere horas de configuración.

4. **Pricing recurrente de academias de gimnasia**: el modelo Stripe es genérico. Configurar tarifas mensuales, packs hermanos, descuentos progresivos probablemente requiere trabajo.

5. **Horarios múltiples por día/semana**: `weekday` (integer, 0-6) + `startTime`/`endTime` (time). Para Akros que tiene varios grupos por hora, esto significa una row por (clase, weekday, hora). Funciona pero requiere crear múltiples rows.

## D. IMPORTANT NON-BLOCKERS

- UX para padres: probablemente existe (auth estándar con Supabase) pero verificar flow de inscripción
- Informes: `scheduled-reports` existe, verificar qué reportes están predefinidos
- Marketing/landing: `(site)/` directory existe — UX pública probable
- Comunicación con padres: `academy-messages` + `notifications` + `push-tokens` existen

## E. NICE-TO-HAVE

- Marketplace (¿para qué sirve? No evalué)
- Soporte tickets (`support-tickets`) — probablemente bueno tener
- AI features — no evaluado

## F. AKROS-SPECIFIC

- Horarios con grupos simultáneos (varios coaches en la misma hora): modelo soporta si creas una clase por grupo
- Disciplinas múltiples (artística + aerial + dance): modelo soporta via `athlete-sport-configs` M:N
- Niveles técnicos + competitivos independientes: schema lo soporta, UI no sé

## G. DOMAIN MODEL VALIDATION

**YES WITH CHANGES** — El modelo PUEDE representar academias recreativas, competitivas, híbridas durante 2-3 años.

Cambios menores necesarios:
- (1) Hacer UI explícita para `levelCode` vs `categoryCode` vs `competitiveLevel` como campos distinguibles
- (2) Añadir modelo de sustituciones temporales (¿`class-coach-assignments.validFrom` + `validTo`?)
- (3) Pricing templates por academia (no codificados)

NO requiere:
- Migración destructiva
- Rebuild del schema
- Cambios de tabla

Riesgos:
- Si no se hace (1), la UX mezclará los conceptos y los entrenadores confundirán nivel interno con categoría federativa
- Si no se hace (2), las sustituciones se gestionarán manualmente via Slack/WhatsApp (lo que ya hace Akros)

## H. FEDERATION READINESS

**Ahora (P0):** NO construir nada.
**Preservar arquitectónicamente:**
- `categoryCode` y `competitiveLevel` como text fields (no enums) — soporta cualquier federación futura
- `federative-licenses` table ya existe — base para expandir
- country/province/city en events — soporta competiciones internacionales

**NO construir:**
- Enums hardcoded de RFEG, FIG, etc.
- Lógica de licencias específica de España
- Integración con APIs de federaciones españolas

**Módulo futuro:** `federations/` con (framework, season, category, license, competition, result) — todo abstracto

## I. EVENT & CAMP READINESS

✅ Schema soporta: `events` con auto-gen, registration, capacity, multiple athletes
⚠️ UX no evaluada para flow de inscripción externa (alumnos no-actuales)
⚠️ Pricing separado para eventos: `competitionTypeCode` permite distinguir pero no hay tabla específica de tarifas por evento

## J. COMMERCIAL OPPORTUNITIES

- `marketplace` table existe (no evaluada)
- `discount-campaigns` permite campañas de captación
- `academy-trials` permite trials
- `lead-management` (tabla `leads`) — pipeline de captación

Cross-sell: el schema `athlete-sport-configs` permite detectar atletas que cumplen criterios de otras actividades. La query es trivial. Falta UX y triggers.

## 10 RESPUESTAS OBLIGATORIAS (preliminar)

1. **¿Podemos vender Zaltyko a Akros mañana?**
   **YES WITH LIMITATIONS** — data model soporta; UX y onboarding son la barrera.

2. **5 principales motivos:**
   - Schema de clases/atletas/eventos cubre Akros 90%+
   - Sport config jerárquico permite multi-disciplina
   - Auto-generación de sesiones reduce trabajo manual
   - athletes-sport-configs table permite nivel interno vs categoría externa
   - withTenant + RLS = arquitectura sólida

3. **Blockers reales (a confirmar):**
   - UX de campos de atleta (nivel interno vs federativo)
   - Substituciones temporales de coaches
   - Onboarding de academia (83 tablas es mucho)
   - Pricing recurrente vs tarifas mensuales
   - (5) UI de calendar/horario para vista Akros

4. **Minimum Viable Changeset:** probablemente BAJO (2-5 cambios de UI + 1-2 docs de onboarding). Sin migración de schema.

5. **Beneficio al ICP general:** 80%+. La mayoría de academias de gimnasia tienen estas mismas estructuras. Akros no es edge case.

6. **¿Modelamos correctamente el dominio?** YES WITH CHANGES (UI changes, schema OK).

7. **¿Cambios estructurales ahora o posponer?** Posponer. NO migrar ahora.

8. **¿Qué NO construir?**
   - Federaciones hardcoded
   - Módulo de camps separado (events cubre)
   - ERP genérico

9. **Si solo P0, ¿Akros podría operar?** Probable YES, con fricción. Para operar cómodamente necesitas P1 también.

10. **Siguiente experimento con 2ª academia:** Una academia NO Akros (evitar sesgo). Sugerencia: academia pequeña (200 alumnos), recreativa pura, sin federación. Comparar gaps.
