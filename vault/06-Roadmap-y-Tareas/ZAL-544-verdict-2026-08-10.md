## 2. Cambio nuclear — cierre del vector ZAL-534

### `hasSubscriptionAccess` (antes)

```ts
export function hasSubscriptionAccess(status: string | null | undefined) {
  return Boolean(status && ACCESS_STATUSES.has(status));
}
```

Bypass: cualquier fila `subscriptions.status IN ('active','trialing','past_due','canceling')` sin respaldo Stripe ⇒ acceso premium. Ese era exactamente el vector ZAL-534.

### `hasSubscriptionAccess` (ahora)

```ts
export function hasSubscriptionAccess(params: {
  stripeSubscriptionId: string | null | undefined;
  status: string | null | undefined;
}) {
  return Boolean(
    params.stripeSubscriptionId &&
      params.status &&
      ACCESS_STATUSES.has(params.status)
  );
}
```

Fail-closed completo: exige simultáneamente `stripeSubscriptionId` truthy **y** `status ∈ ACCESS_STATUSES`. Sin bypass por status, sin bypass por trial, sin bypass por `past_due` o `canceling`. Las dos filas huérfanas detectadas en ZAL-534 (status=active sin stripeSubscriptionId, una premium desde 2025-11-10) devuelven `false` post-merge sin necesidad de migración.

## 9. Separación limpieza + CHECK constraint vs fix de código (per ZAL-534)

La separación es **correcta** y debe mantenerse:

- **Fix de código (este PR)**: cierra el vector. Sin esto, las limpiezas se invalidan la próxima vez que se cree una fila sin respaldo. **Engineerable, testeable, revisable.**
- **Limpieza de filas huérfanas**: requiere DELETE en BD producción (board-only). Una vez ejecutada, las 2 filas premium huérfanas dejan de contar para MRR y acceso.
- **CHECK constraint `stripe_subscription_id IS NOT NULL OR status NOT IN ACCESS_STATUSES`**: defensa en profundidad a nivel BD. Requiere migración remota (board-only). Asegura que el vector no se reintroduzca por bug futuro.

Juntas forman el paquete completo de remediación. Mezclarlas en un solo PR habría mezclado cambios code-bearing (revisables) con writes remotos a producción (board-only) — exactamente el patrón que el régimen de Zaltyko separa.
